1. Introduction

Network hosts such as diskless workstations frequently do not know their protocol addresses when booted; they often know only their hardware interface addresses. To communicate using higher-level protocols like IP, they need a mechanism to discover their protocol address.

Plummer's "Address Resolution Protocol" (ARP) [1] allows a host to discover the hardware address corresponding to a given protocol address. This document describes a protocol — the Reverse Address Resolution Protocol (RARP) — which performs the complementary function: mapping a hardware address to a protocol address.

Historical note: RARP was designed for Ethernet networks but applies to any broadcast medium. It has since been superseded by BOOTP (RFC 951) and DHCP (RFC 2131), which offer significantly more configuration options.

The protocol is designed for use on a broadcast medium such as Ethernet. A host that wishes to determine its protocol address broadcasts a RARP request on the network. A server host, which maintains a database mapping hardware addresses to protocol addresses, responds with the requested information.

2. Design Considerations

The intent of both ARP and RARP is to allow hosts on a broadcast network to dynamically discover address mappings. However, the two protocols differ in important ways:

Why a separate protocol?

One might ask why RARP was proposed as a new protocol rather than an extension to ARP. There are several reasons:

  1. Fundamentally different operations. ARP assumes every host knows its own mappings; RARP requires dedicated servers with a mapping database.
  2. Implementation simplicity. On many systems, ARP is implemented in the kernel. Running an ARP server that responds for other hosts' addresses requires modifications to the kernel. A separate protocol can be handled entirely in user space.
  3. A distinct Ethertype (0x8035) allows network interfaces and packet filters to cleanly distinguish RARP traffic from ARP traffic.

3. The Protocol

The RARP protocol reuses the same packet format as ARP, leveraging the existing, well-understood frame structure. The key distinction lies in the opcode values and the interpretation of the address fields.

3.1 Packet Format

The RARP packet has the identical format to an ARP packet. On an Ethernet, it is encapsulated in a frame with Ethertype 0x8035.

3.2 Opcodes

RARP introduces two new opcodes in addition to ARP's existing pair:

1
ARP Request
Standard ARP request
2
ARP Reply
Standard ARP reply
3
RARP Request
Reverse request — "What is my IP?"
4
RARP Reply
Reverse reply — "Your IP is X"

Opcodes 1 and 2 retain their standard ARP meanings. Any other opcode value is undefined and should be ignored.

3.3 Request Fields (opcode = 3)

When a client sends a RARP request, the fields are interpreted as follows:

ar$sha
Hardware address of the sender
ar$spa
Undefined (sender doesn't know its IP)
ar$tha
Hardware address of the target (often same as ar$sha when asking about itself)
ar$tpa
Undefined (this is what we want to discover)
The request is broadcast on the local network. The Ethernet destination address is set to the broadcast address (FF:FF:FF:FF:FF:FF) so that all RARP servers on the network can hear the request.

3.4 Reply Fields (opcode = 4)

When a RARP server sends a reply, the fields are filled in as follows:

ar$sha
Hardware address of the responder (server)
ar$spa
Protocol address of the responder
ar$tha
Hardware address of the target (copied from request)
ar$tpa
Protocol address of the target — the desired address, looked up from the server's database

The reply is sent directly (unicast) to the requester using its hardware address. The key result is the ar$tpa field, which contains the protocol address the client was seeking.

3.5 Timeouts and Error Handling

Like ARP, RARP does not define explicit "not found" or "error" packet types. If no server on the network has a mapping for the requester's hardware address, no reply will be sent.

The requesting host should set a reasonable timeout. If no reply is received, the request may be retransmitted. Multiple RARP servers may reply to a single request — the client should use the first reply received.

Since multiple RARP servers may exist on a network, a request may generate multiple replies. The client typically accepts the first reply and ignores subsequent ones. This redundancy increases reliability, as the client can still obtain its address if some servers are unavailable.
